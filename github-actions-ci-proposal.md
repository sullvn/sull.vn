**GitHub Actions CI proposal for sullvn/sull.vn**

Reviewed 8 September 2026 · Revised through 13 September 2026 after a seventh review · Proposal only · Temporary review document; remove before merging

Use one required GitHub Actions job, `test`, to install dependencies and run `pnpm test` in the repository’s locked Nix development shell on an arm64 Ubuntu runner. Package scripts define the checks; a branch ruleset requires them before merging into `main`. Fetch the Git LFS images, let Playwright build before serving the site, and control fonts and dates so local and CI screenshots agree.

The existing suite already covers unit tests, Astro diagnostics, a production build, and six Chromium/Firefox visual cases across four routes. The gap is that `pnpm test` omits Biome. Preserve that coverage and the committed Linux screenshots while making the aggregate command complete. [Package scripts](https://github.com/sullvn/sull.vn/blob/9836e696c3a0c072968296ecc4dbb17a663427ac/package.json), [Playwright configuration](https://github.com/sullvn/sull.vn/blob/9836e696c3a0c072968296ecc4dbb17a663427ac/playwright.config.ts), [visual tests](https://github.com/sullvn/sull.vn/blob/9836e696c3a0c072968296ecc4dbb17a663427ac/tests/visual.spec.ts)

This preserves the existing coverage; the six screenshots do not comprehensively test all routes, link destinations, interactions, print styling, or accessibility. Record that boundary without expanding this CI rollout into a broader testing project.

Use this package-script contract:

```json
{
  "build": "astro check && astro build",
  "test": "pnpm test:lint && pnpm test:types && pnpm test:unit && pnpm test:visual",
  "test:lint": "biome ci . && actionlint",
  "test:types": "astro check",
  "test:unit": "node --test",
  "test:visual": "playwright test"
}
```

This is the relevant portion of `scripts`; preserve the other development and formatting commands. Retire `check`, whose operations now have named entries under `test:`. A search of the repository, including the agent configuration, found only `package.json` mentioning it, so no caller needs the old name.

Run every `test:` script from `test` explicitly, including `test:types`. An earlier draft left type checking out of the chain because Playwright’s web server ran `pnpm build`, which called `astro check`. That coupling was invisible in `package.json`, and a later edit to the server command would have silently removed type checking from CI. Change the web-server command to `pnpm exec astro build && pnpm exec astro preview --port 4322 --ignore-lock`, so the suite still builds fresh output before serving it while checking types once. Both halves go through `pnpm exec` so they resolve the binary the same way; the `preview` package script stays for interactive use. `build` keeps its own `astro check` because it is the deployment contract, not a test; nothing in the test path calls it any more, so it stays exactly as it is today. Playwright’s web server runs the command through a shell with the inherited environment and adds nothing to `PATH`, which is why the command uses `pnpm exec` rather than a bare `astro`: an editor or direct invocation has no `node_modules/.bin` on its path. Starting Playwright through `test:visual`, a direct command, or an editor still builds before serving, which avoids a manual-build prerequisite for direct invocations and snapshot updates. A long-lived editor or UI session does not rebuild on every test rerun; restart its test server after changing site source. Astro already checks the repository’s TypeScript and Astro files, so another type checker would duplicate coverage.

| --- | --- |
| `astro check` | 6.5 s |
| `astro build` without an image cache | 2 min 2 s |
| `astro build` again with the image cache | 2.8 s |

The earlier 15-second test run used cached images in `node_modules/.astro`. A fresh build exceeded Playwright’s default 60-second server timeout. Set `webServer.timeout` to `5 * 60 * 1000` initially and `webServer.stdout` to `'pipe'` so Astro’s build output and diagnostics appear in the job log. Five minutes is a starting value to validate against a cold runner, not a measured requirement. These two built-in settings address the timeout and diagnostics while keeping build orchestration inside Playwright. Add an image cache only if measured CI runtime warrants it. When it does, the cold build is almost entirely AVIF encoding, so cache only `node_modules/.astro/assets` with `actions/cache`. Key it on source image hashes, `pnpm-lock.yaml`, `flake.lock`, `astro.config.ts`, and the runner OS and architecture; include any future image-service configuration imported from other files. Do not use restore keys that cross those dependency or configuration boundaries. Astro version and image hashes alone cannot invalidate changes to Sharp, libvips, or global encoder settings. [Playwright web server](https://playwright.dev/docs/test-webserver)

A fresh build can still reuse previously encoded images. In installed Astro 7.3.1, `dist/assets/utils/hash.js` hashes the transform properties and image-service entrypoint, while `dist/assets/build/generate.js` copies an existing local image cache entry without running the encoder. The fourth review reproduced the same transform hash with AVIF quality 80 and 90 even though the encoder options differed; this repository sets that quality in `astro.config.ts`. Before comparing or generating baselines after changing image-service settings or encoder dependencies, run `rm -rf node_modules/.astro/assets` to force re-encoding. Removing `dist/` alone is insufficient. This maintenance rule applies to local builds even while CI has no image cache. [Astro asset caching](https://docs.astro.build/en/guides/images/#asset-caching), [image-service configuration](https://docs.astro.build/en/reference/image-service-reference/#user-configuration)

The explicit `&&` chain stops on failure and returns nonzero. A successful aggregate means every command completed successfully. Keep that list explicit when adding checks; a wildcard selector could unintentionally include a future snapshot-update or interactive script. A custom runner, composite action, or reusable workflow is unnecessary for this single job. [pnpm scripts](https://pnpm.io/cli/run), [GitHub’s guidance on repository scripts](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/add-scripts)

`actionlint` is the one additional checker: this change introduces workflow YAML, and actionlint understands its syntax, expressions, and job dependencies. Add `pkgs.actionlint` to the existing development shell and run it alongside Biome in `test:lint`. Use `biome ci` there: it is Biome’s command for continuous integration and runs the same formatter, lint, and assist checks as `biome check` without ever modifying files, so the script reads as the read-only gate it is; `biome check` stays the interactive form. The locked nixpkgs package wraps the binary with ShellCheck and Pyflakes on its path. The review ran it against the proposed workflow inside a Git repository; it passed with the ShellCheck integration active. actionlint locates workflows from the nearest `.git` entry, whether a directory or the `.git` file of a worktree, so it runs from either. Biome 2.5.11 ignores YAML, so the two tools do not overlap. [actionlint checks](https://github.com/rhysd/actionlint/blob/main/docs/checks.md), [locked actionlint package](https://github.com/NixOS/nixpkgs/blob/42f17a57f4f6e33b3de3dca0a2a5ea5233169d02/pkgs/by-name/ac/actionlint/package.nix)

The Nix shell remains the tool definition. The lockfile selects Node 26.8.1, pnpm 11.25.0, Biome 2.5.11, and Playwright browsers 1.61.1; npm pins `@playwright/test` to 1.61.1. Preserve the existing browser environment settings, but define them in the `mkShell` `env` set instead of `export` lines in `shellHook`, and put `FONTCONFIG_FILE` beside them; the shell then needs no hook. Keep the npm and Nix Playwright versions together: either an npm update or `nix flake update` can break the pairing. Enforce it in the flake rather than in prose; the exact npm pin makes the comparison exact. Use `lib.assertMsg` so the failure names both versions; a bare `assert` prints only the expression it evaluated. A mismatch then fails `nix develop` with a clear message locally and in CI. Attach the assertion to the shell value rather than to the top of the per-system function: `flake-utils` calls that function for every default system to collect its attribute names, and the locked nixpkgs throws for `x86_64-darwin`, which it no longer supports, so an assertion forced there breaks evaluation for every system. The fifth review reproduced that failure with a scratch flake and confirmed that the placement below evaluates and exports the shell variables. The repository’s existing `x86_64-darwin` shell output already fails at this pin; it is unused and outside this change. Replacing `flake-utils` with `lib.genAttrs` over the three supported systems would remove that constraint instead of working around it; treat it as an optional, separate cleanup.

The flake now reads `package.json`, but nix-direnv 3.1.2’s `use flake` watches only `flake.nix`, `flake.lock`, and `devshell.toml`, so a pin change would leave a direnv shell stale until an unrelated reload. The existing `.envrc` bootstrap accepts any nix-direnv from 3.1.0 and otherwise sources 3.1.0, but `nix_direnv_disallow_fallback` first appears in 3.1.1: the seventh review compared the upstream `direnvrc` for 3.0.7, 3.1.0, 3.1.1, and 3.1.2. The development host has 3.1.2 through home-manager, which is why earlier reviews did not notice; a fresh machine would fail to load the environment with an unknown command. Raise the bootstrap to 3.1.2 and replace the whole file; the hash is the SRI digest of the 3.1.2 `direnvrc` from `nix hash file --sri`, the same format as the existing 3.1.0 entry:

```sh
# shellcheck shell=bash
if ! has nix_direnv_version || ! nix_direnv_version 3.1.2; then
  source_url "https://raw.githubusercontent.com/nix-community/nix-direnv/3.1.2/direnvrc" "sha256-Di03ad3a0ueGi6CGrfhrQzyGdQIg9APXIPCAMNQgWYM="
fi
watch_file package.json
nix_direnv_disallow_fallback
use flake . --no-update-lock-file
```

The watcher triggers reevaluation, but nix-direnv normally falls back to its previous working shell when evaluation fails, setting `NIX_DIRENV_DID_FALLBACK=1`. Disallow that fallback so a failed pairing assertion fails environment loading. This does not make an already-open shell current: after fixing an upgrade, leave the old shell and enter a fresh working one before validating baselines. The lockfile flag also matters: `use flake` calls `nix print-dev-env`, which otherwise permits lockfile updates. Pass the flag through so the direnv shortcut rejects incomplete dependency definitions just like the explicit setup command and CI. CI evaluates the flake fresh on every run and needs no direnv configuration. [nix-direnv controls](https://github.com/nix-community/nix-direnv#fine-grained-behavior-control), [pinned implementation](https://github.com/nix-community/nix-direnv/blob/3.1.2/direnvrc), [Nix print-dev-env](https://nix.dev/manual/nix/2.34/command-ref/new-cli/nix3-print-dev-env)

For a paired Playwright upgrade, enter the working development shell before changing either pin. Update nixpkgs as needed, set the exact npm pin to the browser version supplied by that locked nixpkgs revision, and regenerate `pnpm-lock.yaml` with pnpm from the target environment. Then leave the old shell, enter a fresh one, and run the checks and baseline comparison with the new tools. Commit the related manifest and lockfile changes together.

If an already-mismatched checkout prevents shell entry, read the nixpkgs revision from `flake.lock` and obtain pnpm directly from that input, without evaluating the repository shell:

```sh
nix --extra-experimental-features 'nix-command flakes' shell \
  github:NixOS/nixpkgs/LOCKED_NIXPKGS_REV#pnpm
```

Replace `LOCKED_NIXPKGS_REV` with `nodes.nixpkgs.locked.rev`. Use that pnpm to update the exact Playwright pin and npm lockfile to match the intended Nix browser version, then retry the documented `nix develop` command. Keep the pairing assertion active; recovery needs no bypass flag. [Nix shell](https://nix.dev/manual/nix/2.34/command-ref/new-cli/nix3-shell)

The repository tracks `*.png`, `*.jpg`, and `*.avif` with Git LFS. All 20 source images and all six baselines are pointer files in Git. Checkout does not download LFS objects by default, so the original job would have built against three-line pointer files: sharp cannot decode them, and Playwright cannot read the baselines. Set `lfs: true` on the checkout step. LFS downloads from GitHub Actions count against the repository owner’s bandwidth quota. Objects pushed to a fork also count against the owner, and GitHub’s documentation does not say whether they are fetchable from the parent repository before merge, so a fork PR that adds images may fail at checkout; verify this only if fork contributions become relevant.

| Item | Value |
| --- | --- |
| LFS objects at the inspected commit | 26 files, 87,507,548 bytes (83.45 MiB) |
| Free monthly LFS bandwidth for the owner’s personal account | 10 GiB, shared across repositories |
| Complete downloads if the entire allowance is unused | about 122 |

Check the owner’s current usage and actual budget during rollout. Each PR revision uses one download; retries, local clones, forks, and other repositories share the allowance. Changed screenshots also add storage because older LFS versions remain. With a zero-dollar budget, exceeding the allowance blocks LFS until the next month. Add caching only if measured usage calls for it. When it does, the recipe is short: the pointer files are tracked, so `hashFiles('**/*.png', '**/*.jpg', '**/*.avif')` hashes the LFS object IDs and is an exact key for caching `.git/lfs` with `actions/cache`. Check out with `lfs` off, restore the cache, then run `git lfs pull`, which needs no credentials for a public repository. The Actions cache has its own 10 GiB allowance per repository, separate from LFS bandwidth. [LFS billing](https://docs.github.com/en/billing/concepts/product-billing/git-lfs), [LFS attributes](https://github.com/sullvn/sull.vn/blob/9836e696c3a0c072968296ecc4dbb17a663427ac/.gitattributes), [checkout inputs](https://github.com/actions/checkout/blob/3d3c42e5aac5ba805825da76410c181273ba90b1/action.yml)

Both Nix-built test browsers currently read the development host’s system font configuration by the same route. Playwright 1.61.1 runs headless Chromium with the bundle’s separate headless shell executable, an unwrapped binary with fontconfig compiled in, and Firefox is an unwrapped binary linked against Nix’s fontconfig library. Each library reads `/etc/fonts/fonts.conf` by default and honors `FONTCONFIG_FILE`. The bundle’s full Chromium executable, used only with a channel or in headed mode, is instead a wrapper script that defaults `FONTCONFIG_FILE` to a store-generated `fonts.conf` including `/etc/fonts/conf.d`, the user’s XDG font directory, and FHS paths such as `/usr/share/fonts`; the standalone `pkgs.chromium` that `.mcp.json` launches is wrapped the same way, and both honor an existing value. On this host only `DejaVuSans.ttf` from `dejavu_fonts.minimal` is visible, so every system-font stack resolves to DejaVu Sans, including code text. On Ubuntu the same defaults would load the runner’s full font set and rendering rules, which is why an explicit `FONTCONFIG_FILE` is required. Math uses KaTeX’s separate web fonts, so the screenshots are not entirely DejaVu Sans. [Chromium headless shell](https://playwright.dev/docs/browsers#chromium-headless-shell), [KaTeX fonts](https://katex.org/docs/font.html)

Generate one small fontconfig file with `pkgs.writeText` and set `FONTCONFIG_FILE` in the shell. The file lists one font directory, `pkgs.dejavu_fonts.minimal`, and includes the rendering rules by reference to the pinned fontconfig package’s `share/fontconfig/conf.avail` directory rather than restating them: `10-hinting-slight.conf`, `10-yes-antialias.conf`, `10-sub-pixel-none.conf`, `11-lcdfilter-default.conf`, and `90-synthetic.conf`. `90-synthetic.conf` is the finding of the second review, and the LCD-filter rule is the third review’s: a simulation of the shorter list matched the host on every resolved property except `lcdfilter`, which is inert while sub-pixel rendering is off but costs one line to match exactly. The host’s `conf.d` applies the synthetic rules today, so a bold or italic request for DejaVu Sans resolves with `embolden` set and a 0.2 skew matrix, and Skia’s fontconfig backend applies both when rasterizing. Headings use weight 900 or 800, the resume uses `<strong>`, both tested babbles use emphasis, and the Lunchables code blocks use Shiki’s italic tokens, so every baseline depends on these rules. A simulated file with only the font directory and the three rendering rules lost the `embolden` and `matrix` properties; adding the include restored them. Exclude host and user font directories and every other `conf.d` entry. Chromium’s compiled-in fontconfig is a different build from the pinned library that Firefox loads; the rule files are plain XML that either reads. The fifth review ran the file through the pinned `fc-match`: regular, bold, italic, weight-900, and monospace requests resolved to the same properties as the host, including `embolden` and the italic matrix, XDG user fonts stayed invisible, and no cache-directory warning appeared. `makeFontsConf` is unsuitable because its stylesheet always emits the user’s XDG font directory and its default includes are the host `conf.d`; a temporary user setting changed antialiasing under that configuration during the first review. Verify the replacement ignores extra user fonts and user rendering preferences, then treat the first local run after this change as a comparison against the existing baselines: passing the existing visual comparison policy without baseline changes is the goal, and any comparison failure needs an explanation before regeneration. The variable applies to the whole shell, so every fontconfig client started from it renders with this single font, including the Chromium that `.mcp.json` launches for agent screenshots. On this host that changes nothing, because only DejaVu Sans is installed; on a machine with more fonts, agent screenshots will differ from a normal browser. Document that in the README rather than scoping the variable to Playwright, which would need a second variable to carry the store path into `playwright.config.ts`, and Playwright’s launch `env` option replaces the process environment rather than merging with it, so that override would also have to copy `process.env`. A general font-configuration abstraction is unnecessary. Make `formatDate()` in `src/utils/date.ts` format dates in UTC, matching `toIsoDay()`. Frontmatter dates are full timestamps such as `2017-11-02T06:30:20.829Z`, and `toIsoDay()` reduces them to UTC calendar days. UTC is a rendering rule rather than a statement of authorial intent: the post slugs agree with the UTC day for four of the seven posts, with the Los Angeles day for five, and with neither for one, so no single timezone explains them all. UTC is the choice that keeps `toIsoDay()`, `formatDate()`, and the committed baselines consistent, because the host that captured them runs in UTC; moving the site to Pacific days would be a separate content change with new baselines. `formatDate()` currently displays the UTC day `2017-11-02` as November 2 in UTC but November 1 in Los Angeles; the third review reproduced both outputs and confirmed that `timeZone: 'UTC'` fixes them. Those dates are written into the HTML during the build, so changing Playwright’s browser timezone would not fix them. The development host and GitHub’s runners both run in UTC, so this fix protects builds on other machines rather than CI parity. Keep the implementation to the `timeZone: 'UTC'` option. Add one focused test that assigns `process.env.TZ` at runtime, which Node honors, and confirms the same output under UTC and Los Angeles. Restore its original value afterwards, deleting the variable if it was absent; Node runs each test file in its own process, so the restore is hygiene rather than isolation. [Node timezone setting](https://nodejs.org/api/cli.html#tz)

Add `@types/node` to `devDependencies`. The date test reads `process.env`, and the Playwright configuration below reads `process.env.CI`, but nothing declares Node’s type definitions. Under pnpm’s strict layout `node_modules/@types` is empty, and the seventh review found only one route by which those definitions reach the program: a `/// <reference types="node" />` directive in sharp’s type definitions, which Astro’s image-service types import. The existing `node:test` import in `typography.test.ts` type-checks through that accident. Declaring the dependency makes the resolution explicit and survives a change in either package; regenerate the npm lockfile with the pinned pnpm when adding it, and commit both together.
